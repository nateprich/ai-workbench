# Loop-me: think through recurring work

Use for a recurring activity, not as the universal last stage of a project. Establish which recurring problem matters and why. If context is thin, ask about the activity itself; do not start a broad interview about the user's entire life or create a notes database.

Borrow [grilling](grilling.md) for consequential workflow choices. Reach for these concepts only when relevant: what triggers a run, the useful outcome, inputs, who or what does the work, where a human decision belongs, and what happens when a run is incomplete or exceptional. A recurring activity may need no automation, schedule, AI, or checkpoint.

When a human review would help, consider what concise brief would make that decision easier and how much useful preparation can happen first. Preserve the user's desired level of control; do not move consequential checkpoints merely to optimize speed.

Clarify overloaded terms using [domain modeling](domain-modeling.md) when needed. End with an understood recurring pattern or a candidate approach. A full implementer-ready specification is appropriate only when requested. Document any remaining assumptions; building, scheduling, monitoring, and running the workflow require their own authorization.

Adapted from Matt Pocock's in-progress loop-me; see [provenance](../PROVENANCE.md). Automatic notes/spec writes and the requirement to eliminate every implementer question are removed.
